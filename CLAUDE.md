# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Nihilanth Toolbox**: a VS Code extension (publisher `Nihilnia`, id `Nihilnia.nihilanth-toolbox`). It is fully offline, with no network calls or telemetry, and that is a product guarantee. Features: slash-command completions (`/recall`, `/snippet`, `/data`), automatic code memory of JS/TS declarations and deleted fragments, pinned cross-project snippets, deterministic mock data (from presets or local TS types), and selection transforms.

## Commands

```bash
npm run compile            # tsc -> out/ (type-check + test build)
npm run build              # compile, then esbuild bundle -> dist/extension.js, and regenerate THIRD_PARTY_NOTICES.md
npm test                   # compile + node:test unit tests (out/test/core.test.js)
npm run test:integration   # build + run src/test/integration.ts inside a real VS Code via @vscode/test-electron
npm run package            # vsce package -> nihilanth-toolbox-<version>.vsix
```

- Single unit test: `npm run compile && node --test --test-name-pattern="<regex>" out/test/core.test.js`
- The integration runner (`scripts/integration.mjs`) uses the installed VS Code at `%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe`, or `VSCODE_EXECUTABLE_PATH`, and only downloads one if neither exists. Each run creates a throwaway workspace/user-data under `.vscode-test/session-*`.
- F5 ("Run Nihilanth Toolbox" in `.vscode/launch.json`) runs `npm: build` first and then loads `dist/`.
- There is no linter configured. `tsc` in strict mode is the only static check.

## Build/packaging gotchas

- **Two outputs.** `tsc` emits `out/` (used only by tests). esbuild emits `dist/extension.js` (what `package.json#main` points at and what ships). Changing only `out/` has no effect on the running extension.
- **`typescript` and `proper-lockfile` are devDependencies, but they are bundled into `dist/` and used at runtime.** The TS compiler API powers all parsing. `scripts/build.mjs` has a hardcoded list of bundled packages whose licenses go into `THIRD_PARTY_NOTICES.md`. If you add a runtime dependency, add it to that list.
- `.vscodeignore` excludes `src/`, `out/`, `scripts/`, and `node_modules/`, so the VSIX contains only `dist/`, `media/`, and the docs.
- Icon assets (`media/dragon.svg`, `icon.png`, `nihilanth-icons.ttf`) are generated by `scripts/build-icons.py` (needs fonttools + pillow). Marketplace images come from `scripts/generate_marketplace_assets.py`. The integration test checks that the icon font glyph is `\e001`.
- When releasing, bump the version in `package.json` and the README badge/VSIX filename, and add a `CHANGELOG.md` entry.

## Architecture

`src/extension.ts` is the only file that does UI wiring. Most other modules are pure logic with no `vscode` import, so `core.test.ts` can test them under plain Node. `capture.ts` is the exception: it imports `vscode` and is covered only by the integration test.

- **`syntax.ts`**: wrappers around the TS compiler API. `declarations()` pulls named function/class/interface/type/enum/variable declarations with their offsets. `parseLiteral()` is a *safe* literal parser: it tries JSON first, then walks a TS AST that accepts only literal nodes. It never evaluates code, and you should keep it that way. `insideStringOrComment()` suppresses completions inside strings, comments, regexes, and JSX text.
- **`directives.ts`**: `parseDirective()` recognizes `<prefix><command> args` only on a line dedicated to it. It rejects things like `/foo/`, `/usr/bin`, `//`, and `/*`. `parseDataRequest()` parses `/data` args and flags (`--format`, `--seed`, `--edge`) and throws on anything it doesn't know.
- **`generator.ts`**: an LCG `Generator` (seeded means reproducible, and it also fixes the reference date at 2025-01-01). It produces presets and mocks from local TS types, and `formatLiteral` handles JSON vs JS output.
- **`transforms.ts`**: selection transforms (JSON↔object, keys/values/entries, JSON→TS type, dedupe, case conversions). These are built on `parseLiteral` and `formatLiteral`.
- **`model.ts`**: the `MemoryEntry` shape and `searchEntries()` ranking (exact > prefix > substring, then pinned, then recency).
- **`recall.ts`**: `uniqueRecallEntries()` collapses stored versions per name *for display only*; history itself is never deduplicated. It prefers the current file, then the current project, then pinned, then the newest. It skips unpinned captures that fail to parse or contain a `const` with no initializer.
- **`storage.ts`**: `MemoryStore` keeps an append-only JSON Lines log (`memory-v2.jsonl`: a `{version: 2, generation}` header, then `put`/`del`/`touch` operations) in `context.globalStorageUri`, mirrored in an in-memory map.
  - Reads (`list()`) apply only the bytes appended since the last read, and only complete lines. A changed `generation` means another window compacted the file, so the store reloads it.
  - Every write goes through `mutate()`: an in-process queue, then a `proper-lockfile` directory lock, then catching up on the log, applying the operations in memory, LRU eviction of unpinned entries down to `historyLimitMB`, and an append. Compaction (temp file plus atomic rename) runs once the log is over twice the live size.
  - A legacy `memory-v1.json` is imported on the first write and renamed to `.migrated`.
  - A damaged file throws `DamagedMemoryError` and is **never overwritten**. `quarantine()` moves it aside.
  - Capture IDs are a sha256 of project/file/language/name/text. `capture()` records history (removed code). `snapshot()` keeps one `live` mirror of each declaration that currently exists in a file, replacing it in place as you edit. Existing history is never turned into a live entry, so edits can't delete it.
- **`capture.ts`**: `CaptureService` keeps a text buffer for each open, eligible JS/TS document. Eligibility checks workspace trust, language, scheme, size, and the excluded folders/files settings. On destructive edits it diffs against the previous buffer to capture deleted declarations, plus removed fragments of 24 characters to 16 KB that aren't slash commands or whole-document replacements; it only re-parses when a whole identifier was removed. Anything that `looksSecret()` (in `model.ts`) is skipped. Removals wait in `pending`, which recall reads through `pendingEntries()` without writing to disk. After 750 ms idle, or on close or `flush()`, the service writes removals with `capture()` and then the document's declarations with `snapshot()`.
- **`extension.ts`**: `activate()` wires up:
  - the completion provider (triggers `/ ' ' = -`)
  - code actions
  - commands
  - a status bar item
  - an output channel (errors go there through `guard()`, which also shows an error message)

  `activate()` returns `{ store, capture, completionProvider }`. The integration test relies on that return value, so keep it stable. Completion modes:
  - A **directive** on the current line.
  - A **manual session** opened by `nihilanth.open` (Ctrl+Alt+Space), which is time-boxed to one line.
  - **Automatic recall** after 2+ identifier characters in JS/TS. A document-change listener re-runs `editor.action.triggerSuggest` so recall can join a suggestion list that is already open. That is the 0.1.1 regression the integration test guards.

  The internal commands `nihilanth.finish` (it receives the accepted entry's id so the store can refresh its LRU age) and `nihilanth.trigger` are not declared in `package.json`; completion items use them. Completion paths read memory through `memory()`, which merges pending entries and turns a damaged database into an empty list plus a one-time offer to quarantine it. `syntax.ts#sourceFile` caches the last few parses, so the listener and the provider share one parse per keystroke.

## Conventions

- Dense, compact style: long single-line expressions, few comments. Comments exist only to explain non-obvious *why* (for example, in `directives.ts` and `recall.ts`). Match this style and don't reformat.
- Compiler settings: ES2022 target, Node16 modules, `import ts from 'typescript'` default import (`esModuleInterop`).
- New pure logic belongs in a vscode-free module with a test in `src/test/core.test.ts`. Behavior that depends on editor timing or completion belongs in `src/test/integration.ts`.
